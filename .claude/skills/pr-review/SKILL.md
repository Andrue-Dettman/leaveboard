# Reviewing and merging

You own `main`. Nothing lands without passing this checklist. After Phase 0 you never
commit to `main` directly — every change arrives as a PR from `backend/*` or `frontend/*`.

## The loop

```
gh pr list --state open
gh pr view <n>
gh pr checks <n>
gh pr diff <n>
```

Then one of:

```
gh pr review <n> --approve --body "<why it is good>"
gh pr review <n> --request-changes --body "<specific items, with the fix>"
gh pr merge <n> --squash --delete-branch
```

Requesting changes means naming the checklist item that failed, quoting the offending line,
and saying what to do instead. "Please fix the accessibility" is not a review.

## Attribution gate — run this first, on every PR

This repository is a portfolio piece read by a hiring team. Attribution is a merge blocker,
not a style note.

```
gh pr view <n> --json title,body,commits |
  grep -iE "co-authored-by: claude|generated with|claude-session|claude\.ai/code|session_" && echo BLOCKED

git fetch origin && git log --format=%B origin/main..origin/<branch> |
  grep -iE "co-authored-by: claude|generated with|claude-session|session_" && echo BLOCKED
```

Any hit blocks the merge until the owning agent rewrites the branch (`git rebase -i` or
`git commit --amend`) and force-pushes.

Also read the diff for tells that no grep catches:

- Banner comments: `// Generated by`, `// AI-assisted`, `// TODO: human review`
- Emoji anywhere in code, comments, logs, headings, or test names
- Narration comments on obvious code (`// increment counter`), a docblock on every trivial
  function, prose restating a type signature
- A second convention introduced into a file that already had one
- Clever abstractions a student would not write for a project this size
- Docs or PR bodies that mention agents, models, prompts, or how the code was produced

At the end of every phase, grep all of `main` and report the result to the user. It must be
empty:

```
git log --format=%B | grep -iE "co-authored-by: claude|generated with|claude-session|session_"
```

## Every PR

- [ ] CI green. No skipped tests, no `it.only`, no `describe.skip`.
- [ ] Scope is exactly one task row from `docs/DESIGN.md` section 6.5. A PR that also
      "fixed a small thing nearby" gets changes requested — that is how review quality dies.
- [ ] Nothing touched outside the owning directory. T1 in `client/` or T2 in `server/` is
      an automatic block regardless of how good the change is.
- [ ] Request and response shapes match `docs/openapi.yaml`. Diff the schema when unsure;
      do not take the PR description's word for it.
- [ ] `docs/openapi.yaml` is unchanged. Contract edits arrive as their own PR, from you,
      merged before dependent work.
- [ ] Tests cover the happy path and every error path named in the task row.
- [ ] No secrets, no leftover `console.log`, no TODO without a linked issue.
- [ ] Commit messages are conventional-commit, imperative, no emoji.
- [ ] The PR body explains why, in the developer's voice, not just what changed.

## Server PRs

- [ ] Zod validation at the edge, before any query. The parsed value is what gets used.
- [ ] Parameterized queries only. Any interpolated SQL is a block, including `ORDER BY`
      and status filters — those need an allowlist.
- [ ] Error envelope exactly `{ error: { code, message, fields? } }`, correct status per
      code, `fields` keyed by request field names in camelCase.
- [ ] The 403 paths have tests: cancel by a non-requester, cancel of a non-pending request,
      decision by someone who is not the requester's manager, approvals as an employee.
- [ ] Dates handled as `YYYY-MM-DD` strings. Any `new Date('2026-01-01')` used for
      arithmetic is a timezone bug — flag it.
- [ ] No network calls in tests. `fetch` is stubbed.

## Client PRs

Section 4 of `docs/DESIGN.md` in full, plus:

- [ ] A `jest-axe` test exists for every new page and component, and passes.
- [ ] Tab through the feature from the diff. Is the focus order sensible? Does focus land
      somewhere deliberate after every async action?
- [ ] Labels are real `<label for>`. Errors linked with `aria-describedby`, `aria-invalid`
      only when invalid, focus moved to the first invalid field on submit.
- [ ] Dialogs: focus trapped, `Esc` closes, focus returns to the trigger. All three tested.
- [ ] Dynamic updates announced through the shared `LiveRegion`, which is mounted before
      its content changes.
- [ ] Status is never color alone.
- [ ] No fixed widths that break at 320px. Tables collapse to cards under 640px.
- [ ] Tokens used for color and spacing. A raw hex or magic pixel value in a component is
      a comment.
- [ ] No inline styles for layout.
- [ ] Queries are by role and accessible name, not `getByTestId`.

## Running a PR locally

```
gh pr checkout <n>
npm install
npm run lint
npm test
npx @redocly/cli lint
```

For anything touching the database:

```
docker compose up -d db
npm run db:migrate && npm run db:seed
```

## Merge policy

Squash merge only, so `main` reads as one clean commit per task. Delete the branch. The
squash commit message is the PR title — check it is conventional-commit form before
merging, because that is what ends up in the permanent history.

Never merge your own contract PR without telling the user what changed and why.

## Phase discipline

Do not let Phase N+1 work start while Phase N PRs are open. When every task row in a phase
is merged, announce "Phase N closed", run the attribution grep across `main`, and report
what is left.
