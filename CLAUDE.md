# LeaveBoard — agent instructions

Read `docs/DESIGN.md` in full at the start of every session. It is the specification;
this file is the operating manual. Where they disagree, `docs/DESIGN.md` wins.

## What this is

A leave-request tracker built as a portfolio piece for a hiring team to read. Every
file must look like the work of one careful human developer. See "Authorship" below —
it is a merge blocker, not a preference.

## Repository ownership

| Agent       | Owns                                                        | Never touches    |
| ----------- | ----------------------------------------------------------- | ---------------- |
| T1 Backend  | `server/`, `docs/API.md`, server ADRs                       | `client/`        |
| T2 Frontend | `client/`, `docs/ACCESSIBILITY.md`, front-end ADRs          | `server/`        |
| T3 Reviewer | `main`, CI, `README.md`, `docs/CONTRIBUTING.md`, deployment | feature branches |

`docs/openapi.yaml` is the frozen contract. Neither builder edits it directly: if you
need a change, run `gh issue create` describing the change and stop work on that task.
T3 makes and merges the contract PR before dependent work continues.

## Hard rules

1. Never commit to `main`. Only T3 merges, and only via `gh pr merge --squash` after review.
2. Stay inside the directory you own. Cross-boundary needs become issues, not edits.
3. One PR per task from the phase tables in `docs/DESIGN.md` section 6.5. Small PRs.
4. Every PR must pass CI before you request review.
5. Start each new task from a fresh branch off `origin/main` so you pick up merged work.
6. Do not relitigate stack decisions (`docs/DESIGN.md` section 3.1). They are final.

## Commands

Run from the repository root:

```
npm install            # install both workspaces
npm test               # vitest in client and server
npm run lint           # eslint across the monorepo
npm run format:check   # prettier verification (CI runs this)
```

Per workspace:

```
npm run dev:server     # API on http://localhost:3001
npm run dev:client     # Vite dev server on http://localhost:5173
npm run db:migrate     # apply SQL migrations
npm run db:seed        # load Maria, Sam, Priya and the leave types
```

Local database (Docker):

```
docker compose up -d db
```

Copy `server/.env.example` to `server/.env` and `client/.env.example` to `client/.env`
before running either dev server.

## Definition of done

**Server work:** input validated with Zod before any query, parameterized queries only,
error envelope shape from `docs/DESIGN.md` section 3.4, tests covering the happy path
and every error path named in the task including the 403 cases.

**Client work:** section 4 of `docs/DESIGN.md` in full. A page is not finished until its
`jest-axe` test passes with zero violations and it is operable by keyboard alone.

## Authorship and attribution

This repository is a portfolio piece that will be read by a hiring team. Everything in it
must read as the work of one human developer. These rules are non-negotiable.

**Commits and PRs**

- Never add `Co-Authored-By: Claude ...`, `Generated with [Claude Code]`,
  `Claude-Session: ...`, or any `claude.ai/code/session_...` URL to a commit message, PR
  title, or PR body. If you notice your tooling is about to append one, write the commit
  message explicitly with `git commit -m "<message>"` and nothing else.
- Commit messages: conventional-commit style, imperative mood, first person implied, no
  emoji. `feat(server): add business-day calculation` — not `Add business day calc`.
- PR bodies are written in the developer's voice ("I chose X because..."), never
  "Claude implemented..." or "This AI-generated PR...".
- Do not add yourself as a GitHub reviewer, assignee, or contributor by any name.

**Code and comments**

- No banner comments like `// Generated by ...`, `// AI-assisted`, `// TODO: human review`,
  or references to prompts, agents, models, or sessions anywhere in source, tests, configs,
  or docs.
- Comment only what a careful human would comment: non-obvious decisions and tricky logic.
  Do not narrate obvious code (`// increment counter`), do not add a docblock to every
  trivial function, do not restate the type signature in prose.
- No emoji in code, comments, logs, README headings, or test names.
- Match the file's existing style exactly; don't introduce a second convention. Prefer
  plain, idiomatic code over clever abstractions a student would not write.
- Test names describe behavior (`rejects end date before start date`), not implementation,
  and never mention what "the model" or "the agent" did.
- Documentation (README, ADRs, API docs) is written in first person singular where a voice
  is needed and never mentions AI tooling, agents, or how the code was produced.

**Enforcement**

A `commit-msg` hook in `.githooks/` strips attribution trailers, and `.claude/settings.json`
disables them. Both are backstops, not permission to rely on them. T3 greps every PR branch
and all of `main` after each phase; any hit blocks the merge until the branch is rewritten.

## Skills

At the start of every session, list the skills in `.claude/skills/` and `~/.claude/skills/`,
then load the ones for your role:

- T1 Backend: `api-contract`, plus any global express / node-testing / postgres / openapi skill
- T2 Frontend: `a11y-first-react`, plus any global frontend-design / react / accessibility / css skill
- T3 Reviewer: `pr-review`, plus any global code-review / github / security-review skill

If an assigned skill does not exist, say so and proceed with the guidance in `docs/DESIGN.md`.
